# النسخ الاحتياطي والاستعادة

> **قاعدة:** مفتاح فك التشفير (الخاص) لا يوضع أبداً في GitHub أو Vercel أو Supabase أو أي ملف في المستودع. احتفظ به أنت فقط، في مكانين آمنين على الأقل (مثلاً مدير كلمات مرور، ونسخة ورقية أو على ذاكرة USB في خزنة).

## ما الذي يُنسخ

| الطبقة | ماذا تحمي | أين |
|---|---|---|
| نسخ Supabase اليومية (خطة Pro، 7 أيام) | القاعدة كاملة | لوحة Supabase ← Database ← Backups |
| نسختنا اليومية المشفرة | القاعدة (بما فيها حسابات الدخول) + **كل ملفات الصور** + ملف بيان | تخزين خارجي (Cloudflare R2 أو Backblaze B2) |

نسخ Supabase **لا تشمل ملفات Storage**، لذلك نسختنا الخاصة ضرورية.

كل نسخة (سير `Backup` في GitHub Actions، يومياً 00:15 بتوقيت الرياض):

1. `roles.sql` و`schema.sql` و`data.sql`: الأدوار والمخطط والبيانات (عبر `supabase db dump`).
2. `storage/`: كل الملفات، مع `storage-manifest.json` فيه حجم وبصمة SHA-256 لكل ملف.
3. `manifest.json`: عدد صفوف الجداول الأساسية، وآخر سطر في سلسلة التدقيق (رقمه وبصمته)، وبصمة كل ملف.
4. الكل في أرشيف واحد مشفر بأداة [age](https://age-encryption.org) بمفتاحك العام. GitHub يملك المفتاح العام فقط: يستطيع التشفير ولا يستطيع فك التشفير.
5. يُرفع إلى `daily/<التاريخ>/`، وأول نسخة في كل شهر تُحفظ أيضاً في `monthly/<الشهر>/`.
6. الاحتفاظ: 30 نسخة يومية و12 نسخة شهرية (يُحذف الأقدم تلقائياً).
7. تُسجَّل النتيجة في جدول `backup_runs`، ويظهر في «الإعدادات ← النسخ الاحتياطي» للمدير العام. عند الفشل، أو إذا مرت 36 ساعة بلا نسخة ناجحة في الإنتاج، يصل إشعار للمدير العام، ويرسل GitHub بريداً بفشل السير.

آخر بصمة في سلسلة التدقيق تُحفظ مع كل نسخة **خارج Supabase**، فلو عبث أحد بالسجل داخل القاعدة يظهر الفرق عند المقارنة.

## الإعداد (مرة واحدة)

### 1. مفتاح التشفير

على جهازك (ثبّت age من الرابط أعلاه، أو `winget install FiloSottile.age` على Windows):

```
age-keygen -o green-o-backup.key
```

- الملف `green-o-backup.key` هو **المفتاح الخاص**: احفظه كما في القاعدة أعلاه، ثم احذفه من الجهاز.
- السطر `Public key: age1...` الذي يطبعه الأمر هو **المفتاح العام**: هذا وحده يوضع في GitHub.

### 2. التخزين الخارجي

مثال Cloudflare R2:

1. أنشئ حاوية (Bucket) باسم مثل `green-o-backups`، بلا وصول عام.
2. أنشئ مفتاح API بصلاحية «Object Read & Write» على هذه الحاوية فقط.
3. سجّل: رابط الـ S3 للحساب (`https://<account-id>.r2.cloudflarestorage.com`)، وAccess Key ID، وSecret Access Key.

(Backblaze B2 مشابه: حاوية خاصة، ومفتاح تطبيق محصور بها، ورابط S3 للمنطقة.)

### 3. GitHub

Settings ← Environments ← New environment باسم `production`، ويُفضَّل «Required reviewers» إن أردت. ثم داخل البيئة:

**Variables** (ليست سرية):

| الاسم | القيمة |
|---|---|
| `BACKUP_SUPABASE_URL` | رابط مشروع الإنتاج `https://<ref>.supabase.co` |
| `BACKUP_AGE_RECIPIENT` | المفتاح العام `age1...` |
| `BACKUP_S3_BUCKET` | اسم الحاوية |
| `BACKUP_S3_ENDPOINT` | رابط الـ S3 |

**Secrets** (سرية):

| الاسم | القيمة |
|---|---|
| `BACKUP_DATABASE_URL` | رابط اتصال القاعدة من Supabase ← Connect ← Session pooler (مع كلمة مرور القاعدة) |
| `BACKUP_SUPABASE_SECRET_KEY` | مفتاح secret لمشروع الإنتاج |
| `BACKUP_S3_ACCESS_KEY_ID` | من الخطوة 2 |
| `BACKUP_S3_SECRET_ACCESS_KEY` | من الخطوة 2 |

### 4. التجربة الأولى

Actions ← Backup ← Run workflow. بعد انتهائه: تأكد من وجود الملف في الحاوية، ومن ظهور السطر في «الإعدادات ← النسخ الاحتياطي». إذا لم تكتمل الإعدادات، يتخطى السير النسخ ويكتب تنبيهاً بما ينقص.

## الاستعادة

**الاستعادة ليست زراً داخل التطبيق**، عمداً. اختر السيناريو:

| المشكلة | الحل |
|---|---|
| خطأ في سجلات محددة (مثلاً حُذفت بيانات بالخطأ) | لا تستعد شيئاً. ابحث في «سجل التدقيق» عن القيم القديمة وأعد إدخالها. |
| تلف في القاعدة | لوحة Supabase ← Database ← Backups ← Restore لأحدث نسخة سليمة. (لا يعيد ملفات الصور، لكنها لم تتأثر.) |
| فقدان المشروع كله | الخطوات أدناه، إلى مشروع Supabase جديد. |

### استعادة كاملة إلى مشروع جديد

تحتاج جهازاً عليه: Docker، وNode 24، وage، وأداة `psql` (مع PostgreSQL 17)، ونسخة من المستودع.

1. **أنشئ مشروع Supabase جديداً** بالمنطقة نفسها. لا تطبّق الترحيلات عليه: المخطط يأتي من النسخة.
2. **نزّل النسخة** من الحاوية (`daily/...` أو `monthly/...`) وفك تشفيرها:
   ```
   age -d -i green-o-backup.key -o backup.tar.gz green-o-<التاريخ>.tar.gz.age
   tar -xzf backup.tar.gz
   cd green-o-<التاريخ>
   ```
3. **استعد القاعدة** (رابط Session pooler للمشروع الجديد):
   ```
   psql --single-transaction --variable ON_ERROR_STOP=1 \
     --file roles.sql \
     --file schema.sql \
     --command 'SET session_replication_role = replica' \
     --file data.sql \
     --dbname "<رابط القاعدة الجديدة>"
   ```
   `session_replication_role = replica` يوقف المشغّلات أثناء الإدخال، فتعود سلسلة التدقيق كما كانت بالضبط.
4. **استعد الملفات** (من مجلد المستودع، والمتغيران للمشروع الجديد):
   ```
   NEXT_PUBLIC_SUPABASE_URL=https://<ref الجديد>.supabase.co SUPABASE_SECRET_KEY=<المفتاح> \
     node scripts/backup/storage.mts upload <مسار مجلد النسخة>/storage
   ```
5. **تحقق** (المتغيرات نفسها):
   ```
   node scripts/backup/verify-restore.mts <مسار مجلد النسخة>
   ```
   يتحقق من عدد الصفوف، ومن أن سلسلة التدقيق سليمة وتنتهي عند آخر سطر في النسخة ببصمته نفسها، ومن وجود كل ملف ببصمته. أي اختلاف يُطبع ويخرج الأمر بخطأ.
6. **أعد الربط**:
   - في Vercel: حدّث `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` و`SUPABASE_SECRET_KEY` للمشروع الجديد، ثم أعد النشر.
   - في Supabase الجديد: أعد ضبط الإشعارات بـ `configure_push_dispatch` (انظر docs/deploy.md، القسم 7)، لأن أسرار Vault لا تُنسخ.
   - في Supabase ← Authentication: أعد إعداداتها (إيقاف التسجيل الذاتي، طول كلمة المرور...) كما في docs/deploy.md.
   - في GitHub: حدّث متغيرات وأسرار `production` للنسخ الاحتياطي.
7. **ادخل بحساب** وتأكد من المهام والصور، وشغّل «سجل التدقيق ← تحقق الآن».

## ما يُختبر تلقائياً

في كل تشغيل لـ CI: يُنسخ القاعدة والملفات من Supabase المحلي، وتُشفَّر بمفتاح مؤقت، ثم يُفك التشفير وتُفحص الملفات، ويُشغَّل `verify-restore` على النسخة (`scripts/ci/backup-round-trip.sh`). الاستعادة إلى مشروع ثانٍ لا تُختبر تلقائياً، ولذلك تمرين الاستعادة أعلاه ضروري.
