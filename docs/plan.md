# خطة تنفيذ نظام إدارة المصنع (green-o)

> الخطة المعتمدة بتاريخ 2026-11-10. أي تغيير أثناء التنفيذ يُسجَّل في [decisions.md](decisions.md).

## السياق

- **المطلوب:** نظام عربي بالكامل (RTL) لإدارة مصنع واحد، بواجهتين: لوحة إدارة للكمبيوتر، وتطبيق جوال PWA للموظفين. يغطي المستخدمين والمهام والصيانة والإنتاج والإشعارات والتقارير وسجل التدقيق والنسخ الاحتياطي.
- **الوضع عند كتابة الخطة:** لا يوجد كود سابق، فالبناء يبدأ من الصفر.
- **مستودع GitHub:** أنشأتَ المستودع `https://github.com/Mohammad1-creator/green-o`، وفيه commit واحد على `main` يحتوي `README.md` فقط. المستودع **عام** حالياً (انظر المخاطر). سأرفع إليه كل تغيير أولاً بأول.
- **بيئة التطوير:** Windows مع Node وgit. نحتاج Docker لتشغيل Supabase محلياً ولاختبارات الصلاحيات (انظر المرحلة 0).
- **النتيجة المطلوبة:** نظام تُفرض صلاحياته داخل قاعدة البيانات نفسها، ويُبنى على 14 مرحلة صغيرة تختبر كل واحدة منها بنفسك قبل الانتقال للتي بعدها.

## 1. المعمارية

```
 [لوحة الإدارة: متصفح الكمبيوتر]        [تطبيق الجوال PWA: آيفون / أندرويد]
                 \                                /        ▲  إشعار Push
                  ▼                              ▼         │
        Vercel: تطبيق Next.js واحد (App Router)          خوادم Push (Apple / Google)
          - Server Components: القراءة بجلسة المستخدم             ▲
          - Server Actions: الكتابة + تحقق Zod                    │
          - /api/push/dispatch: يرسل Web Push بمفتاح VAPID ───────┘
                  │                         ▲
                  ▼                         │ pg_net (عند كل إشعار جديد)
        Supabase: Postgres (RLS + دوال RPC + Triggers + pg_cron + pg_net)
                  Auth · Storage (حاويات خاصة) · Realtime (إشعارات فورية)

        GitHub Actions: CI + ترحيلات القاعدة + نسخ احتياطي يومي مشفّر ← تخزين خارجي
```

| القرار | السبب |
|---|---|
| تطبيق Next.js واحد يخدم الواجهتين (`/admin` للإدارة و`/m` للجوال) | الكود والأنواع والمصادقة مشتركة، والنشر واحد. الواجهتان تختلفان في التصميم فقط. |
| القراءة عبر Server Components، والكتابة عبر Server Actions | المنطق والمفاتيح تبقى على الخادم، ولا يصل للمتصفح إلا المفتاح العام (publishable). |
| كل خطوة في سير العمل دالة Postgres (RPC) تتحقق من الصلاحية والحالة معاً. يشمل ذلك: الاستلام، الإنهاء، الاعتماد، الإعادة، إسناد الإصلاح، تسجيل الكميات | القاعدة تُفرض حتى لو تجاوز أحد الواجهة واتصل بالـAPI مباشرة. وقفل الصف يمنع تجاوز الكميات عندما يسجّل عاملان في اللحظة نفسها. |
| RLS على كل جدول، إضافة إلى فحص الصلاحية في كل Server Action | دفاع بطبقتين، والمرجع النهائي هو RLS. |
| الدور والقسم يُقرآن من جدول `profiles` داخل السياسات، وليس من claims داخل JWT | تغيير الدور أو إيقاف الحساب يسري فوراً بدل الانتظار حتى ينتهي التوكن (قد يستغرق ساعة). مع أقل من 200 مستخدم الكلفة مهملة. |
| الدخول برقم الموظف: يتحول داخلياً إلى بريد اصطناعي ثابت مثل `<الرقم>@staff.<نطاق داخلي>` | Supabase Auth يعمل بالبريد أو الهاتف. بهذه الطريقة نحصل جاهزاً على تشفير كلمات المرور والجلسات والحماية من التخمين، ولا يرى الموظف البريد أبداً. |
| تسجيل الدخول يتم من المتصفح مباشرة إلى Supabase، وليس من خادم Vercel | Supabase يحدّ عدد محاولات الدخول لكل عنوان IP. لو مرّ الدخول عبر خادم Vercel لظهر كل المستخدمين بعنوان واحد وتشاركوا الحد نفسه. |
| المهام المجدولة (التذكيرات، الصيانة الوقائية، إعادة محاولة Push) تعمل بـ pg_cron داخل Supabase | تعمل بجانب البيانات بلا خادم إضافي، ويُحسب "اليوم" بتوقيت المصنع داخل SQL. |
| جدول `notifications` هو مصدر كل الإشعارات: كل إشعار جديد يستدعي عبر pg_net مساراً في Next.js يرسله بمكتبة `web-push` | طريق واحد لكل الإشعارات، سواء أطلقها مستخدم أو جدولة، مع حفظ حالة الإرسال وإعادة المحاولة. لا حاجة إلى Firebase. |
| Realtime على جدول الإشعارات | الإشعار يظهر داخل التطبيق فوراً بلا تحديث للصفحة، وRealtime يحترم RLS. |
| Storage بحاويات خاصة وروابط موقّعة قصيرة العمر وسياسات مبنية على مسار الملف | الصورة لا يفتحها إلا من يحق له رؤية المهمة أو البلاغ المرتبط بها. |
| أنواع TypeScript مولّدة من القاعدة (`supabase gen types`)، وZod للتحقق من المدخلات | الأنواع متطابقة من القاعدة إلى الواجهة، ونفس مخطط التحقق يُستخدم في النموذج وعلى الخادم. |
| Tailwind بالخصائص المنطقية (`ms-` و`ps-` و`start-`) مع `<html lang="ar" dir="rtl">` | اتجاه RTL صحيح بلا CSS مكرر. |
| تنسيق التواريخ والأرقام بـ `Intl` بالمحلّي `ar-u-nu-latn-ca-gregory` وبالمنطقة الزمنية المحفوظة في الإعدادات | المحلّي `ar-SA` وحده يعطي أرقاماً هندية وتقويماً هجرياً. هذا المحلّي يفرض أرقاماً غربية وتقويماً ميلادياً. |
| Service Worker للإشعارات والتثبيت فقط، بلا أي تخزين مؤقت | التزاماً بالقرار: لا وضع عدم اتصال. |
| مكونات shadcn/ui (مبنية على Radix) مع `DirectionProvider` بقيمة rtl | مكونات جاهزة ومناسبة لذوي الاحتياجات، والكود ملكنا فنعدّله للـRTL كما نشاء. |
| ترحيلات القاعدة بـ Supabase CLI داخل المستودع، وتُطبّق على dev ثم prod من GitHub Actions | المخطط نفسه في البيئتين، ولا تعديل يدوي على الإنتاج. |

## 2. تصميم قاعدة البيانات

### 2.1 مبادئ عامة
- المعرّفات `uuid`، والأوقات `timestamptz` مخزنة بتوقيت UTC وتُعرض بتوقيت المصنع. كل جدول فيه `created_at` و`updated_at` و`created_by`.
- لا حذف فعلي للسجلات الأساسية، بل تعطيل بحقل `is_active` حفاظاً على التاريخ.
- أرقام مقروءة للمهام والبلاغات والأوامر، مثل `T-000123` و`F-000045` و`P-000012`.
- قيود في القاعدة نفسها: `NOT NULL` و`CHECK` (حدود الطول والقيم الموجبة) و`FOREIGN KEY` وأنواع `enum`.
- ثلاثة مخططات (schemas):
  - `public`: الجداول ودوال RPC المتاحة عبر الـAPI.
  - `private`: دوال الصلاحيات، وهو غير مكشوف في الـAPI.
  - `audit`: سجل التدقيق، وهو غير مكشوف في الـAPI.
- دور `anon` لا يملك أي صلاحية على أي جدول، لأن النظام كله يتطلب تسجيل الدخول.

- مجموع الكمية السليمة والمعيبة المسجلة في أي مرحلة لا يتجاوز مدخلها.
- مدخل المرحلة الأولى هو كمية الأمر.
- مدخل كل مرحلة بعدها هو مجموع الكمية السليمة في المرحلة السابقة.
- يُرفض إلغاء أي إدخال إذا كان الإلغاء سيجعل مرحلة لاحقة تتجاوز مدخلها.

### 2.4 كيف تُفرض الصلاحيات
- **دوال مساعدة في `private`:** `my_role()` و`my_department()` و`is_active_user()` و`is_gm()` و`manages_department(dept)` و`is_maintenance_manager()` و`is_production_manager()` و`can_view_task(id)` و`can_manage_task(id)` و`can_view_fault(id)` و`can_view_order(id)`. كلها `SECURITY DEFINER` و`STABLE` بمسار بحث فارغ (`search_path = ''`).
- **كل سياسة تبدأ بفحص** `is_active_user()`، فالحساب الموقوف يُمنع فوراً.
- **العمليات البسيطة** مثل الآلات والمنتجات والأقسام تُكتب مباشرة بجلسة المستخدم، وتحكمها سياسات RLS للإدراج والتعديل مع صلاحيات على مستوى الأعمدة.
- **خطوات سير العمل** دوال RPC تتحقق صراحة من الدور والنطاق والحالة الحالية.
- **مفتاح secret** (البديل الأحدث لـ service_role) يُستخدم على الخادم في موضعين فقط: عمليات حسابات الدخول (إنشاء حساب، إعادة تعيين كلمة المرور، الإيقاف)، ومسار إرسال Push. كل ما عداهما يعمل بجلسة المستخدم، فتطبَّق عليه RLS ويُسجَّل الفاعل في التدقيق.
- **الأداء:** نستخدم صيغة `(select auth.uid())` في السياسات، ونضع فهارس على كل عمود تستخدمه السياسات.
- **سجل التدقيق:**
  - يُكتب عبر trigger عام على كل جدول مهم.
  - لا يملك أي دور صلاحية `UPDATE` أو `DELETE` أو `TRUNCATE` عليه، ولا حتى service_role.
  - trigger إضافي يرفض أي تعديل أو حذف.
  - سلسلة تجزئة (hash chain): كل سطر يحمل بصمة السطر الذي قبله، فيُكتشف أي تلاعب.

### 2.5 مصفوفة الصلاحيات

**الرموز:** ق = قراءة، ك = كتابة (إنشاء وتعديل)، قسمه = بيانات قسم المدير، المُسند = ما أُسند إليه، — = لا شيء.

| المورد | المدير العام | مدير الصيانة | مدير الإنتاج | الموظف |
|---|---|---|---|---|
| الإعدادات (اسم المصنع، المنطقة الزمنية) | ق، ك | ق | ق | ق |
| الأقسام | ق، ك | ق | ق | ق |
| دليل الأسماء (الاسم، الدور، القسم) | ق، ك | ق | ق | ق |
| بيانات الموظف (الرقم، الهاتف…) وكلمة المرور | ق، ك للجميع | ق قسمه، وك لموظفي قسمه فقط | ق قسمه، وك لموظفي قسمه فقط | ق نفسه فقط |
| تعيين الأدوار ونقل موظف بين الأقسام | ك | — | — | — |
| الفرق وأعضاؤها | ق، ك | ق، ك قسمه | ق، ك قسمه | ق فرقه |
| المهام: إنشاء، تعديل، إسناد، اعتماد، إعادة، إلغاء | ق، ك الكل | ق، ك مهام قسمه | ق، ك مهام قسمه | ق المُسند فقط |

| الإشعارات | إشعاراته | إشعاراته | إشعاراته | إشعاراته (ويعلّمها مقروءة) |
| الآلات | ق، ك | ق، ك | ق | ق |

| أوامر الإنتاج ومراحلها وإسناد العمال | ق، ك | — | ق، ك | ق المُسند |
| تسجيل الكميات والعيوب | ق، ك | — | ق، ك (نيابة عن العامل، وإلغاء إدخال بسبب) | ك لنفسه على مرحلته المُسندة، وق إدخالاته |
| التقارير ولوحات المؤشرات والتصدير | الكل | الصيانة + مهام قسمه | الإنتاج + مهام قسمه | — |
| سجل التدقيق | ق | — | — | — |
| حالة النسخ الاحتياطي | ق | — | — | — |
| تعديل سجل التدقيق أو حذفه | لا أحد، ولا حتى مفتاح الخدمة | | | |

### 2.6 دورة حياة المهمة

| من | إلى | من يستطيع | شرط |
|---|---|---|---|
| جديدة | مستلمة | المُسند إليه | — |
| جديدة أو مستلمة | قيد التنفيذ | المُسند إليه | يُسجَّل الاستلام تلقائياً إن لم يكن مسجلاً |
| قيد التنفيذ | بانتظار الاعتماد | المُسند إليه | ملاحظة اختيارية |
| بانتظار الاعتماد | مكتملة | مدير القسم أو المدير العام | — |
| بانتظار الاعتماد | تحتاج متابعة | مدير القسم أو المدير العام | السبب إلزامي |
| تحتاج متابعة | قيد التنفيذ | المُسند إليه | — |
| أي حالة غير نهائية | ملغاة | مدير القسم أو المدير العام | السبب إلزامي |

حالتا "مكتملة" و"ملغاة" نهائيتان. شارة "متأخرة" تظهر عندما يمر موعد الاستحقاق والمهمة لم تُسلَّم بعد للاعتماد.

## 4. مراحل العمل

كل مرحلة تنتهي بتقرير فيه: ملخص ما اكتمل، والمشاكل المتبقية، وخطوات الاختبار. لا أبدأ المرحلة التالية إلا بعد موافقتك.

### المرحلة 0: التأسيس والبيئتان
**ما سيُبنى:**
- ربط المجلد بمستودعك على GitHub:
  - نبني فوق الـcommit الموجود على `main`، فلا نكتب فوقه.
  - نُنشئ فرع `dev`.
  - نضيف هذه الخطة في `docs/plan.md`، ونوسّع `README.md` بوصف المشروع وطريقة تشغيله.
  - نضيف `.gitattributes` لتوحيد نهايات الأسطر بين Windows وخوادم Linux.
- Next.js (أحدث إصدار مستقر) مع TypeScript بالوضع الصارم، وTailwind، وESLint وPrettier، وVitest، وPlaywright.
- تخطيط أساسي RTL، وخط عربي (IBM Plex Sans Arabic عبر `next/font`، يُستضاف مع التطبيق)، ومكونات shadcn/ui الأساسية.
- Supabase CLI كاعتمادية داخل المشروع، ويعمل محلياً على Docker.
- مشروعا Supabase: `green-o-dev` و`green-o-prod` (خطة Pro).
- مشروع Vercel واحد: فرع `main` للإنتاج، وفرع `dev` لبيئة التطوير برابط ثابت، ولكل بيئة متغيراتها الخاصة.
- إعدادات الدخول في المشروعين: إيقاف التسجيل الذاتي، وإيقاف تأكيد البريد، وحد أدنى لطول كلمة المرور.
- شريط "بيئة التطوير" يظهر في dev فقط، وصفحة `/health` تعرض اسم البيئة وحالة الاتصال بالقاعدة.
- CI يشغّل: الفحص (lint)، وفحص الأنواع، والاختبارات، والبناء، وسكربتاً يفحص ملفات المتصفح الناتجة ويفشل إن وجد فيها أي مفتاح سري، وأداة gitleaks التي تفحص كل commit بحثاً عن أسرار.

**ما أحتاجه منك:**
- تثبيت Docker Desktop.
- إنشاء حسابي Supabase وVercel (حساب GitHub جاهز).
- عند أول رفع قد تفتح نافذة تسجيل دخول GitHub في المتصفح. وافق عليها مرة واحدة.
- يُفضَّل تحويل المستودع إلى خاص قبل إعداد CI والنسخ الاحتياطي (انظر المخاطر).
- إدخال المفاتيح السرية بنفسك في لوحات Vercel وGitHub. لن أطلب منك لصقها في المحادثة.

**كيف تختبرها:**
- افتح رابط dev: ترى صفحة عربية من اليمين لليسار، مع شريط "بيئة التطوير" وعبارة "متصل بقاعدة dev".
- افتح رابط الإنتاج: لا يظهر الشريط، وتظهر عبارة "متصل بقاعدة prod".

**تنتهي عندما:**
- الكود مرفوع على فرعي `dev` و`main` في GitHub، وCI ناجح.
- الرابطان يعملان، كلٌّ بقاعدته.
- فحص الأسرار يكتشف مفتاحاً وهمياً نضعه مؤقتاً على جهازك فقط، ولا نرفعه.

### المرحلة 1: الدخول والأقسام والمستخدمون، وأساس سجل التدقيق
**ما سيُبنى:**
- الجداول: `app_settings` و`environment_marker` و`departments` و`profiles` و`employee_details`، مع دوال الصلاحيات وسياسات RLS.
- أساس سجل التدقيق: الجدول، والـtrigger العام، ومنع التعديل والحذف، وسلسلة التجزئة. يُربط من هذه المرحلة فصاعداً بكل جدول مهم.
- صفحة الدخول (رقم الموظف وكلمة المرور)، وتسجيل الخروج، وتجديد الجلسة، وتوجيه كل دور لواجهته: الإدارة إلى `/admin`، والموظف إلى `/m`.
- إدارة الأقسام (للمدير العام).
- إدارة المستخدمين ضمن النطاق المسموح: إنشاء، تعديل، إيقاف وتفعيل، إعادة تعيين كلمة المرور. إنشاء المستخدم يتم على ثلاث خطوات:
  1. تحقق من صلاحية المنفّذ.
  2. إنشاء حساب الدخول.
  3. إنشاء الملف الشخصي عبر RPC بجلسة المدير، فيُسجَّل في التدقيق من قام بذلك.

  إذا فشلت الخطوة الثالثة يُحذف حساب الدخول تلقائياً.
- صفحة الإعدادات: اسم المصنع والمنطقة الزمنية.
- سكربت `bootstrap-admin` لإنشاء أول مدير عام (يُشغَّل مرة واحدة لكل بيئة).
- سكربت البيانات التجريبية لـ dev، بثلاث حمايات (تفاصيلها في القسم 6).

**كيف تختبرها:**
- ادخل كمدير عام، وأنشئ قسمي الصيانة والإنتاج ومديريهما وبعض الموظفين.
- ادخل كمدير الإنتاج: لا ترى موظفي الصيانة.
- أوقف حساب موظف: لا يستطيع الدخول، ويُمنع فوراً حتى لو كانت جلسته مفتوحة.
- نفّذ أمراً جاهزاً سأعطيك إياه يحاول قراءة بيانات قسم آخر مباشرة من الـAPI: النتيجة فارغة.

**تنتهي عندما:** تنجح اختبارات pgTAP لمصفوفة صلاحيات هذه الجداول، ولا يبقى جدول بلا RLS، ويُرفض تعديل سجل التدقيق.

### المرحلة 2: هيكل تطبيق الجوال والإشعارات وPush
جعلتها مبكرة عمداً، لأن Push على آيفون أكبر مخاطرة تقنية في المشروع.

**ما سيُبنى:**
- بيان PWA وأيقونات (عادية وmaskable وapple-touch-icon)، وService Worker للإشعارات فقط، وصفحة "طريقة التثبيت" لآيفون وأندرويد.
- واجهة الجوال: شريط سفلي، واحترام حواف الشاشة (النوتش)، وأزرار كبيرة سهلة اللمس.
- جدولا `notifications` و`push_subscriptions`، وجرس الإشعارات مع عدّاد فوري عبر Realtime، وصفحة الإشعارات مع تعليمها مقروءة.
- زر "تفعيل الإشعارات" يطلب الإذن بضغطة من المستخدم، كما يشترط آيفون.
- آلية الإرسال:
  - مسار الإرسال في Next.js.
  - trigger يستدعيه عبر pg_net، والسرّ المشترك محفوظ في Vault داخل Supabase.
  - إعادة محاولة كل 5 دقائق.
  - حذف الاشتراكات المنتهية تلقائياً.
- زر "إرسال إشعار تجريبي لنفسي".

**ما أحتاجه منك:** جهاز آيفون (iOS 16.4 أو أحدث) وجهاز أندرويد للتجربة.

**كيف تختبرها:**
- ثبّت التطبيق على آيفون: من Safari اضغط "مشاركة" ثم "إضافة إلى الشاشة الرئيسية".
- ثبّته على أندرويد من Chrome بخيار "تثبيت".
- فعّل الإشعارات وأغلق التطبيق، ثم اضغط "إشعار تجريبي" من الكمبيوتر بالحساب نفسه.
- يصل الإشعار إلى الجوال، والضغط عليه يفتح الصفحة الصحيحة.

**تنتهي عندما:** يصل الإشعار على الجهازين والتطبيق مغلق، ويظهر داخل التطبيق فوراً بلا تحديث.

### المرحلة 3: الفرق والمهام (النواة)
**ما سيُبنى:**
- الفرق وأعضاؤها، ويديرها مدير كل قسم لقسمه.
- جداول `tasks` و`task_assignees` و`task_events` مع سياسات RLS.
- إنشاء مهمة: عنوان، ووصف، وموعد استحقاق اختياري، وإسناد لموظف أو فريق من قسم المدير.
- في لوحة الإدارة: قائمة المهام مع مرشحات، وصفحة تفاصيل المهمة.
- في الجوال: شاشة "مهامي"، وتفاصيل المهمة، وتسجيل "شاهدها" تلقائياً عند فتحها، وزر "استلمتها".
- يرى المدير لكل عضو في الفريق: من شاهد ومن استلم ومتى.
- إشعار "مهمة جديدة" يصل للمُسند إليهم.

**كيف تختبرها:**
- أنشئ مهمة لفريق من 3 أشخاص: يصل الإشعار للثلاثة.
- افتح المهمة بحساب أحدهم: يظهر عند المدير "شاهدها: فلان".
- موظف من قسم آخر لا يرى المهمة حتى لو فتح رابطها المباشر.

**تنتهي عندما:** تنجح اختبارات صلاحيات المهام.

### المرحلة 4: دورة حياة المهمة والاعتماد
**ما سيُبنى:**
- دوال RPC لكل انتقال في جدول 2.6.
- شارة "متأخرة".
- صندوق "بانتظار اعتمادي" للمديرين في لوحة الإدارة وفي الجوال.
- الخط الزمني للمهمة: كل انتقال، ومن قام به، ومتى، وسببه.
- الإشعارات: عند الإنهاء يُشعَر المدير، وعند الاعتماد أو الإعادة يُشعَر المُسند إليهم.

**كيف تختبرها:**
- موظف يُنهي مهمة، والمدير يحاول إعادتها بلا سبب: يُرفض الطلب.
- يعيدها المدير مع ذكر السبب: تصبح "تحتاج متابعة"، ويصل السبب للموظف.
- يُنهيها الموظف مرة أخرى، ويعتمدها المدير: تصبح "مكتملة".
- موظف يحاول اعتماد مهمته بنفسه عبر الـAPI مباشرة: يُرفض الطلب.
- مهمة موعدها أمس تظهر عليها شارة "متأخرة".

**تنتهي عندما:** تنجح اختبارات كل انتقال مسموح وكل انتقال ممنوع.

### المرحلة 5: التعليقات والصور والتذكيرات
**ما سيُبنى:**
- التعليقات على المهام، مع إشعار للمشاركين فيها.
- رفع الصور من الكاميرا أو المعرض:
  - تُضغط الصورة على الجهاز قبل الرفع.
  - تُحفظ في حاوية خاصة، وتُعرض بروابط موقّعة.
  - تُفرض حدود النوع والحجم على الخادم وفي الحاوية نفسها.
- التذكيرات: يحدد المدير وقتاً أو أكثر لكل مهمة، ومهمة pg_cron كل دقيقة ترسل التذكير المستحق لمن لم يُنهِ المهمة.

**كيف تختبرها:**
- صوّر من الجوال وأرفق الصورة بمهمة: تظهر عند المدير.
- انسخ رابط الصورة وافتحه بحساب لا يحق له رؤيتها: يُرفض.
- ضع تذكيراً بعد دقيقتين: يصلك إشعار Push.

**تنتهي عندما:** تنجح اختبارات سياسات Storage، ولا يُرسل أي تذكير مرتين.

### المرحلة 6: الصيانة: الآلات والأعطال والإصلاح
**ما سيُبنى:**
- سجل الآلات، ويديره مدير الصيانة.
- "الإبلاغ عن عطل" في الجوال ولوحة الإدارة، متاح لأي مستخدم: الآلة، والوصف، وصورة، وهل الآلة متوقفة.
- صندوق البلاغات لمدير الصيانة: يسند الإصلاح (فتُنشأ مهمة إصلاح لموظف أو فريق صيانة)، أو يرفض البلاغ مع ذكر السبب.
- عند اعتماد مهمة الإصلاح: يُغلق البلاغ، وتعود الآلة إلى حالة "تعمل"، ويُشعَر المبلِّغ.
- سجل أعطال وإصلاحات لكل آلة.

**كيف تختبرها:**
- موظف إنتاج يبلغ عن عطل: يصل إشعار لمدير الصيانة.
- يسند مدير الصيانة الإصلاح لفني، والفني ينهيه، والمدير يعتمده: يرى المبلِّغ "تم الإصلاح".
- يحاول مدير الإنتاج ثم المدير العام إسناد إصلاح: يُرفض الطلب في الحالتين.

**تنتهي عندما:** تنجح اختبارات قاعدة "مدير الصيانة وحده يُسند الإصلاح".

### المرحلة 7: الصيانة الوقائية الدورية
**ما سيُبنى:**
- خطط دورية لكل آلة: كل N يوم أو أسبوع أو شهر، وتاريخ البداية، وأيام الإنشاء المسبق، والمُسند إليه.
- مهمة pg_cron كل ساعة تنشئ المهام المستحقة حسب توقيت المصنع، مع قيد فريد يمنع التكرار.
- شاشة "المواعيد القادمة"، ومؤشر الالتزام بالصيانة الوقائية.

**كيف تختبرها:**
- أنشئ خطة يومية تبدأ اليوم: تظهر مهمتها خلال ساعة، أو فوراً بزر "تشغيل الآن" المتاح في dev فقط.
- شغّل التوليد مرتين متتاليتين: تبقى مهمة واحدة فقط.

**تنتهي عندما:** تنجح اختبارات حدود اليوم (منتصف الليل بتوقيت الرياض مقابل UTC) واختبارات منع التكرار.

### المرحلة 8: الإنتاج: المواصفات والمنتجات والمسارات
قبل هذه المرحلة سأطلب منك تأكيد افتراضات الإنتاج (الافتراضات 21 إلى 27 في القسم 7)، لأن خطأها يغيّر تصميم الجداول.

**ما سيُبنى:**
- شاشة تعريف المواصفات، مثل "السماكة: رقم، بالمليمتر، من 1 إلى 50" أو "اللون: قائمة خيارات".
- نموذج المنتج يُبنى تلقائياً من التعريفات.
- تحقق مزدوج: Zod يُولَّد من التعريفات على الخادم، وtrigger في القاعدة.
- قائمة المراحل، ومحرر مسار المنتج (اختيار المراحل وترتيبها)، وأنواع العيوب.

**كيف تختبرها:**
- أضف مواصفة جديدة: تظهر في نموذج المنتج فوراً، بلا تدخل مبرمج.
- أرسل قيمة خاطئة مباشرة عبر الـAPI، مثل نص في حقل رقمي: ترفضها القاعدة.

**تنتهي عندما:** تنجح اختبارات التحقق من المواصفات.

### المرحلة 9: الإنتاج: الأوامر والكميات والعيوب
**ما سيُبنى:**
- إنشاء أمر إنتاج (المنتج، والكمية، وتاريخ التسليم)، مع نسخ مسار المنتج إليه.
- إسناد عمال لكل مرحلة.
- في الجوال: شاشة "مراحلي"، وتسجيل الكمية السليمة والمعيبة ونوع العيب.
- عرض "المتاح لهذه المرحلة" لحظياً، فتعمل المراحل بالتوازي.
- إلغاء إدخال مع ذكر السبب (للمدير)، وإغلاق المرحلة، وإغلاق الأمر.
- شاشة تقدّم الأمر.

**كيف تختبرها:**
- أمر بكمية 100. القص يسجل 60 سليمة و5 معيبة.
- التصفيح يرى 60 متاحة ويبدأ العمل والقص ما زال مستمراً.
- محاولة تسجيل 70 في التصفيح تُرفض.
- عاملان يسجلان في اللحظة نفسها: لا يتجاوز المجموع المدخل المتاح.

**تنتهي عندما:** تنجح اختبارات قيود الكمية والتسجيل المتزامن.

### المرحلة 10: التقارير ولوحات المؤشرات والتصدير
**ما سيُبنى:**
- لوحة مؤشرات لكل دور (القائمة في الافتراض 30)، مع مرشح للفترة والقسم.
- تصدير Excel بورقة من اليمين لليسار، وتصدير CSV بترميز UTF-8 مع BOM حتى يقرأ Excel العربية سليمة.
- صفحات مهيأة للطباعة وحفظ PDF.
- التقارير تُبنى على استعلامات تحترم RLS، فكل دور يرى نطاقه فقط تلقائياً.

**كيف تختبرها:**
- صدّر تقرير المهام وافتحه في Excel: العربية سليمة والأرقام غربية.
- اطبع تقرير أمر إنتاج: يخرج PDF مرتب.
- صدّر تقريراً بحساب مدير الإنتاج: لا تظهر فيه أرقام الصيانة.

**تنتهي عندما:** تطابق أرقام اللوحات عدّاً يدوياً على البيانات التجريبية.

### المرحلة 11: سجل التدقيق (الواجهة والتحقق)
**ما سيُبنى:**
- صفحة سجل التدقيق للمدير العام، مع بحث بالفاعل ونوع التغيير والتاريخ، وعرض القيم قبل التغيير وبعده.
- تحقق يومي من سلسلة التجزئة.
- تصدير السجل.

**كيف تختبرها:**
- عدّل مهمة: يظهر سطر جديد في السجل بالقيم قبل وبعد.
- حاول تعديل أو حذف سطر من السجل، ولو بمفتاح الخدمة: يُرفض.

**تنتهي عندما:** تنجح اختبارات منع التعديل واختبارات التحقق من السلسلة.

### المرحلة 12: النسخ الاحتياطي والاستعادة
**ما سيُبنى:**
- سير عمل يومي في GitHub Actions بعد منتصف الليل بتوقيت المصنع، ينفّذ:
  - نسخ القاعدة: الأدوار والمخطط والبيانات، بما فيها حسابات الدخول.
  - نسخ ملفات Storage.
  - تشفير النسخة ورفعها إلى تخزين خارجي بسياسة احتفاظ.
  - تسجيل النتيجة في `backup_runs`، وإرسال تنبيه عند الفشل.
- دليل استعادة خطوة بخطوة، وسكربت تحقق يُشغَّل بعد الاستعادة.

**ما أحتاجه منك:**
- حساب تخزين خارجي، مثل Cloudflare R2 أو Backblaze B2.
- أن تحتفظ أنت بمفتاح فك التشفير في مكان آمن.

**كيف تختبرها:** تمرين استعادة كامل لنسخة dev في مشروع مؤقت (قاعدة الإنتاج ستكون شبه فارغة قبل الإطلاق). بعد الاستعادة: ادخل بحساب، وتحقق من الأعداد والصور وسلسلة التدقيق.

**تنتهي عندما:** تنجح الاستعادة، ويُسجَّل زمنها في الدليل.

### المرحلة 13: التقوية والإطلاق
**ما سيُبنى ويُراجَع:**
- مراجعة أمنية كاملة:
  - Security Advisor في Supabase بلا أي خطأ.
  - رؤوس HTTP الأمنية.
  - `npm audit`.
  - مراجعة كل دالة `SECURITY DEFINER`.
- قياس الأداء على الجوال، واختبار شامل على الأجهزة الحقيقية.
- تطبيق الترحيلات على prod، وإنشاء المدير العام في prod، وربط النطاق إن وُجد.
- دليل استخدام قصير لكل دور.

**كيف تختبرها:** قائمة قبول نهائية تمر عليها بنفسك على الإنتاج بحسابات حقيقية.

**تنتهي عندما:** توافق أنت على الإطلاق، وتنجح أول نسخة احتياطية للإنتاج ويتم التحقق منها.

## 5. خطة الاختبارات

1. **اختبارات RLS والصلاحيات (pgTAP عبر `supabase test db`):**
   - بيانات ثابتة للاختبار: 3 أقسام، ومستخدم من كل دور في كل قسم، وبيانات متقاطعة بين الأقسام.
   - لكل جدول ولكل دور ولكل عملية: اختبار لما يُسمح به، واختبار لما يُمنع.
   - اختبارات عامة على القاعدة كلها:
     - لا جدول بلا RLS.
     - لا صلاحيات لـ `anon`.
     - كل دالة `SECURITY DEFINER` بمسار بحث ثابت.
     - سجل التدقيق لا يقبل التعديل ولا الحذف.
   - اختبارات قواعد العمل: انتقالات المهام، والسبب الإلزامي، وإسناد الإصلاح لمدير الصيانة وحده، وحدود الكميات، وعدم تكرار الصيانة الوقائية، وحدود اليوم بتوقيت المصنع.
2. **اختبارات الوحدات (Vitest):**
   - مخططات Zod، ومولّد التحقق من المواصفات المرنة.
   - تنسيق التاريخ والأرقام (أرقام غربية، تقويم ميلادي، توقيت المصنع).
   - منطق "متأخرة"، وحساب الكمية المتاحة للعرض.
   - تحويل رقم الموظف إلى بريد الدخول، وتوليد Excel وCSV.
3. **اختبارات التكامل:**
   - استدعاء الـAPI مباشرة بتوكن كل دور، متجاوزاً الواجهة، للتأكد من أن كل ما هو ممنوع مرفوض فعلاً.
   - إرسال مدخلات مزوّرة إلى Server Actions، مثل تغيير `department_id` أو `status`: تُرفض.
4. **اختبارات شاملة (Playwright):**
   - المسارات الأساسية لكل دور، على مقاس الكمبيوتر وعلى مقاس جوال (محاكاة iPhone وPixel).
   - سيناريو المهمة الكامل: إنشاء، ثم استلام، ثم إنهاء، ثم إعادة، ثم إنهاء، ثم اعتماد.
   - سيناريو البلاغ والإصلاح، وسيناريو تسجيل الكميات.
   - لقطات شاشة للتحقق من اتجاه RTL.
5. **التجربة اليدوية على الجوال (قائمة في كل مرحلة تمس الجوال):**
   - التثبيت على آيفون وأندرويد.
   - وصول Push والتطبيق مغلق والشاشة مقفلة.
   - التصوير والرفع على شبكة جوال بطيئة.
   - لوحة الأرقام في حقول الكميات.
   - حواف الشاشة (النوتش)، وحجم الخط، والاتجاه.
6. **فحوص الأمان في CI:**
   - gitleaks على كل commit.
   - فحص ملفات المتصفح بحثاً عن أي مفتاح سري.
   - `npm audit`.
   - Security Advisor في Supabase قبل كل نشر للإنتاج.

**متى تعمل الاختبارات في GitHub Actions:**
- كل رفع إلى `dev`: الفحص، والأنواع، واختبارات الوحدات (البند 2)، وgitleaks.
- عند تغيّر ملفات `supabase/`: إضافة إلى ما سبق، اختبارات القاعدة (البند 1) والتكامل (البند 3) على Supabase محلي.
- طلب الدمج إلى `main`: كل البنود من 1 إلى 4.

هذا التقسيم يوفّر دقائق GitHub Actions، وهي محدودة شهرياً إذا صار المستودع خاصاً.

## 6. النشر والبيئات والنسخ الاحتياطي

### البيئتان

| | التطوير (dev) | الإنتاج (prod) |
|---|---|---|
| الفرع | `dev` | `main` |
| Vercel | بيئة Preview برابط ثابت للفرع | بيئة Production |
| Supabase | `green-o-dev` (مجاني أو Pro) | `green-o-prod` (Pro) |
| البيانات | تجريبية فقط | حقيقية فقط |
| مفاتيح VAPID وسرّ الإرسال | خاصة بها | خاصة بها |
| النشر | تلقائي عند الدمج في `dev` | بعد موافقة يدوية في GitHub Environments |

### مسار النشر
1. أرفع كل تغيير مباشرة إلى فرع `dev` على GitHub، فيعمل CI مع كل رفع.
2. بعد الدمج: تُطبَّق الترحيلات على قاعدة dev، ثم يُنشر التطبيق على رابط dev.
3. بعد تجربتك وموافقتك على المرحلة: طلب دمج من `dev` إلى `main`، ثم موافقة يدوية، ثم تُطبَّق الترحيلات على قاعدة prod، **ثم** يُنشر التطبيق.
   - النشر التلقائي في Vercel لفرع `main` يكون معطّلاً، ويتم النشر عبر Deploy Hook، لضمان أن القاعدة تُحدَّث قبل التطبيق.
4. الترحيلات متوافقة مع الإصدار السابق: نضيف أولاً، ثم نحذف القديم في نشر لاحق.

### المتغيرات والمفاتيح

| المتغير | مكانه | سري؟ |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | المتصفح والخادم | لا |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | المتصفح والخادم | لا، وRLS تحمي البيانات |
| `SUPABASE_SECRET_KEY` | الخادم فقط | نعم |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | المتصفح | لا |
| `VAPID_PRIVATE_KEY` | الخادم فقط | نعم |
| `PUSH_DISPATCH_SECRET` | الخادم + Vault في Supabase | نعم |
| `APP_ENV` | الخادم (`dev` أو `prod`) | لا |

**قواعد ثابتة:**
- لا يبدأ أي متغير سري بـ `NEXT_PUBLIC_`.
- كل ملف يستخدم مفتاحاً سرياً يستورد `server-only`، فيفشل البناء لو استُورد في كود المتصفح.
- فحص CI على ملفات المتصفح الناتجة.
- `.env.local` مستبعد من git.
- تفعيل التحقق بخطوتين على حسابات GitHub وSupabase وVercel.

### عزل البيانات التجريبية عن الإنتاج
1. البيانات التجريبية موجودة فقط في `supabase/seed/dev.sql` و`scripts/seed-dev.ts`، ولا تدخل الترحيلات أبداً.
2. السكربت يرفض العمل إلا إذا تحققت الشروط الثلاثة معاً:
   - `APP_ENV=dev`.
   - معرّف مشروع Supabase في الرابط هو معرّف مشروع dev.
   - `environment_marker` في القاعدة نفسها قيمته `dev`.
3. الترحيلات تُطبَّق على prod دائماً بلا خيار `--include-seed`.
4. لا تتشارك البيئتان أي مفتاح.

### النسخ الاحتياطي والاستعادة

| الطبقة | ما تحميه | ملاحظات |
|---|---|---|
| نسخ Supabase Pro اليومية (تُحفظ 7 أيام) | القاعدة كاملة | استعادة من لوحة Supabase. يتوقف النظام مؤقتاً أثناءها، ويمكن فقدان بيانات حتى يوم كامل. |
| الاستعادة لنقطة زمنية (PITR) | فقدان دقائق فقط بدل يوم | إضافة مدفوعة اختيارية، نفعّلها إن كان فقدان يوم غير مقبول. |
| نسخنا الخاصة اليومية المشفرة في تخزين خارجي | القاعدة (بما فيها حسابات الدخول) + ملفات الصور | نسخ Supabase **لا تشمل ملفات Storage**، لذلك تُنسخ الملفات منفصلة. الاحتفاظ: 30 نسخة يومية و12 شهرية. مع كل نسخة تُحفظ آخر بصمة في سلسلة التدقيق. |

**سيناريوهات الاستعادة (في `docs/backup-restore.md`):**
- **خطأ في سجلات محددة:** تُصحَّح من القيم القديمة المحفوظة في سجل التدقيق، بلا استعادة كاملة.
- **تلف في القاعدة:** استعادة من نسخ Supabase اليومية.
- **فقدان المشروع:**
  1. إنشاء مشروع Supabase جديد.
  2. استعادة نسختنا الخاصة والملفات إليه.
  3. تحديث المتغيرات في Vercel وأسرار Vault.

**الاستعادة ليست زراً داخل التطبيق،** وذلك عمداً، لأنها عملية خطرة. تُنفَّذ بالدليل.

**تمرين الاستعادة:** كل 3 أشهر، وبعد كل تغيير كبير في المخطط.

### الافتراضات
هذه قواعد لم تُذكر في طلبك. لن أعتمد أياً منها نهائياً حتى توافق أو تصحّح.

**الأدوار والمستخدمون**
1. المدير العام يملك صلاحية الكتابة في كل شيء، **إلا إسناد الإصلاح**، التزاماً بكلمة "وحده". إن أردت السماح له فالتغيير بسيط.
2. الأدوار أربعة فقط. مدير الصيانة مرتبط بقسم الصيانة، ومدير الإنتاج بقسم الإنتاج. أي قسم جديد بلا مدير يديره المدير العام، وإضافة دور "مدير قسم" عام ممكنة لاحقاً.
3. مدير القسم ينشئ ويعدّل ويوقف موظفي قسمه، ويعيد تعيين كلمات مرورهم. لا يستطيع إنشاء مديرين، ولا تغيير الأدوار، ولا نقل موظف بين الأقسام؛ هذه للمدير العام فقط.
4. دليل الأسماء (الاسم، والدور، والقسم) مرئي لكل من سجّل الدخول، لأن الأسماء تظهر في المهام والتعليقات والبلاغات. بيانات الموظف التفصيلية مثل رقم الموظف والهاتف مقيّدة بالنطاق.
5. البيانات المرجعية مرئية للجميع لأن الموظف يحتاجها للاختيار والعرض: أسماء الآلات، والمنتجات، والمراحل، والأقسام.
6. الموظف لا يغيّر كلمة مروره بنفسه، والمدير هو من يعيد تعيينها.
7. لا يُحذف أي مستخدم، بل يُوقَف حسابه حفاظاً على التاريخ.
8. المديرون يستطيعون استخدام تطبيق الجوال أيضاً: يرون ما أُسند إليهم، وصندوق "بانتظار اعتمادي"، ويستطيع مدير الصيانة إسناد الإصلاح منه.
9. الفريق داخل قسم واحد، والموظف يمكن أن يكون عضواً في أكثر من فريق في قسمه.

**المهام**

10. ينشئ المهام المديرون والمدير العام فقط. الموظف لا ينشئ مهاماً.
11. عند الإسناد لفريق، تُسجَّل أسماء أعضائه لحظة الإسناد؛ من ينضم للفريق لاحقاً لا تصله المهام القديمة.
12. في مهمة الفريق: أي عضو يستطيع تقديمها، وتصبح "مستلمة" عند أول عضو يستلمها، ويُسجَّل لكل عضو وقت مشاهدته واستلامه.
13. حالة "تحتاج متابعة" هي حالة المهمة بعد أن يعيدها المدير مع السبب.
14. موعد الاستحقاق اختياري، والمهمة بلا موعد لا تصبح متأخرة أبداً. المهمة التي سُلّمت للاعتماد قبل موعدها لا تُعتبر متأخرة. الشارة تظهر فقط، بلا إشعار إضافي.
15. لا يمكن إعادة فتح مهمة مكتملة أو ملغاة؛ تُنشأ مهمة جديدة بدلها.
16. التذكيرات يحددها المدير يدوياً لكل مهمة، ولا يوجد تذكير تلقائي افتراضي.
17. التعليقات لا تُعدَّل ولا تُحذف. الصور المرفقة يحذفها المدير العام أو مدير القسم فقط، ويُسجَّل الحذف في التدقيق.
18. الإشعارات الافتراضية:
    - مهمة جديدة: للمُسند إليهم.
    - مهمة أُنجزت: لمدير القسم.
    - اعتماد أو إعادة: للمُسند إليهم.
    - تعليق جديد: للمشاركين في المهمة.
    - تذكير: للمُسند إليهم.
    - بلاغ عطل جديد: لمدير الصيانة.
    - إصلاح تم أو بلاغ رُفض: للمبلِّغ.
    - إسناد مرحلة إنتاج: للعمال.

**الصيانة**

19. كل بلاغ مرتبط بآلة مسجلة. حالات البلاغ: مفتوح، أُسند إصلاحه، تم الإصلاح، مرفوض مع سبب.
    - البلاغ يراه: المبلِّغ، ومدير قسمه، ومدير الصيانة، والفني المُسند إليه، والمدير العام.
    - مدة التوقف تُحسب من وقت البلاغ إلى وقت الإصلاح، إن أشار المبلِّغ إلى أن الآلة متوقفة.
20. الصيانة الوقائية تتبع جدولاً ثابتاً يبدأ من تاريخ البداية، ولا يتأثر بتاريخ إنجاز المرة السابقة.
    - إذا تعطّل النظام وفاتت مواعيد، تُنشأ مهمة واحدة لآخر موعد فائت فقط.
    - تُنشأ مهمة جديدة في موعدها حتى لو كانت السابقة لم تُغلق بعد.

**الإنتاج (للتأكيد قبل المرحلة 8)**

21. مسار المنتج سلسلة مرتبة من المراحل. "التوازي" يعني أن المرحلة التالية تبدأ على الكمية السليمة الجاهزة من المرحلة السابقة قبل أن تنتهي. المسارات المتفرعة، مثل مرحلتين مستقلتين تندمجان لاحقاً، غير مدعومة في الإصدار الأول.
22. وحدة القياس واحدة في كل مراحل المنتج، بلا تحويل بين المراحل (مثل لوح واحد يُقص إلى 4 قطع). الكميات تقبل الكسور العشرية.
23. المواصفات على مستوى المنتج. كل اختلاف في المواصفات (مثل سماكة مختلفة) منتج مستقل. إن احتجت مواصفات مختلفة لكل أمر، فنستخدم الآلية نفسها على الأمر.
24. الكمية المعيبة تُستبعد ولا تنتقل للمرحلة التالية، ولا توجد دورة لإعادة التصنيع.
25. العامل يسجّل كمياته بنفسه على مرحلته المُسندة، ولا يعدّلها بعد الحفظ. مدير الإنتاج يسجّل نيابة عنه، أو يلغي إدخالاً مع ذكر السبب، وكل ذلك يُسجَّل في التدقيق.
26. مدير الإنتاج هو من يغلق المرحلة. ويكتمل الأمر عند إغلاق آخر مرحلة.
27. يوجد قسم إنتاج واحد.

**عام**

28. الواجهة بالوضع الفاتح فقط، ولكل موظف جوال خاص به.
29. تغيير اسم المصنع يظهر فوراً داخل التطبيق، لكن اسم أيقونة التطبيق المثبّت على آيفون لا يتغير إلا بإعادة التثبيت. تغيير المنطقة الزمنية يؤثر على العرض وعلى حساب "اليوم" من لحظة التغيير، ولا يغيّر البيانات المخزنة.
30. المؤشرات الافتراضية:
    - **المهام:** العدد حسب الحالة، والمتأخرة، ونسبة الإنجاز في الوقت، ومتوسط زمن الإنجاز، وعدد الإعادات، لكل موظف وفريق وقسم.
    - **الصيانة:** البلاغات المفتوحة، ومتوسط زمن الاستجابة، ومتوسط زمن الإصلاح، ومدة التوقف لكل آلة، وأكثر الآلات أعطالاً، ونسبة الالتزام بالصيانة الوقائية.
    - **الإنتاج:** الأوامر حسب الحالة، والكمية السليمة لكل مرحلة ومنتج وعامل، ونسبة العيوب حسب المرحلة والنوع، والكمية المنتظرة في كل مرحلة، والأوامر المتأخرة عن موعد التسليم.
31. سجل التدقيق يُحفظ للأبد. يُسجَّل فيه كل إنشاء أو تعديل أو تعطيل في:
    - المستخدمين، والأقسام، والفرق.
    - المهام وحالاتها.
    - الآلات، والبلاغات، وخطط الصيانة.
    - المواصفات، والمنتجات، والمسارات، والأوامر، وإدخالات الكميات وإلغاؤها.
    - الإعدادات، وحذف الصور، وإعادة تعيين كلمات المرور.
32. أقصى فقدان مقبول للبيانات يوم واحد (أو دقائق إن فعّلنا PITR)، وزمن الاستعادة المستهدف بضع ساعات.

## 8. طريقة العمل بعد الموافقة

- أنفّذ مرحلة واحدة فقط، ثم أعطيك: ملخص ما اكتمل، والمشاكل المتبقية، وخطوات الاختبار. أنتظر موافقتك قبل المرحلة التالية.
- أرفع كل تغيير إلى GitHub (فرع `dev`) أولاً بأول كما طلبت، برسائل commit واضحة. الدمج في `main` (الإنتاج) يتم فقط بعد موافقتك على المرحلة.
- لا أستخدم force push أبداً، ولا أرفع أي ملف فيه أسرار.
- أطلب إذنك قبل أي إجراء على حساباتك في Supabase وVercel.
- أسجّل كل افتراض تؤكده أو تصححه في `docs/decisions.md`.

### التحقق الشامل قبل الإطلاق
"يوم عمل تجريبي" كامل على بيئة dev، بحسابات من كل دور على كمبيوتر وجوالين حقيقيين:
1. المدير العام ينشئ قسماً وموظفين.
2. مدير الصيانة ينشئ خطة صيانة وقائية، وتتولد مهمتها تلقائياً.
3. موظف إنتاج يبلغ عن عطل بصورة، ومدير الصيانة يسنده، والفني ينهيه، والمدير يعيده مرة مع سبب ثم يعتمده.
4. مدير الإنتاج ينشئ أمراً بثلاث مراحل، ويسجل عاملان كميات وعيوباً بالتوازي.
5. تصل الإشعارات على الجوالين والتطبيق مغلق.
6. تُصدَّر التقارير إلى Excel وPDF وتُطابَق أرقامها.
7. يظهر كل ما سبق في سجل التدقيق، والسلسلة سليمة.
8. تُؤخذ نسخة احتياطية وتُستعاد في مشروع مؤقت بنجاح.
